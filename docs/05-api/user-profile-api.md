## 1. Overview

The User Profile Management API allows an authenticated user to retrieve their own profile and update their display name. The API derives the user's identity from the validated JWT rather than accepting a user ID from the request body.

The API returns selected profile fields only. The password hash is not exposed.

## 2. Authentication

Include the access token returned by the authentication API in the HTTP `Authorization` header:

```http
Authorization: Bearer <accessToken>
```

Requests without a valid token are rejected with HTTP `401 Unauthorized`.

## 3. Endpoints

### 3.1 Get the authenticated user's profile

**Endpoint:** `GET /users/me`

Returns the profile belonging to the authenticated user.

**Successful response:** `200 OK`

Example response:

```json
{
  "id": "user-uuid",
  "name": "Test Student",
  "email": "student@example.com",
  "role": "STUDENT",
  "createdAt": "2026-01-01T00:00:00.000Z",
  "updatedAt": "2026-01-02T00:00:00.000Z"
}
```

The timestamps above are illustrative. Actual values are generated by the application.

**Possible errors**

- `401 Unauthorized` â€” token is missing or invalid.
- `404 Not Found` â€” the profile associated with the authenticated user ID does not exist.

### 3.2 Update the authenticated user's profile

**Endpoint:** `PATCH /users/me`

Updates the authenticated user's display name.

**Request body**

```json
{
  "name": "Updated Student"
}
```

**Successful response:** `200 OK`

The response contains the updated profile using the same safe fields as `GET /users/me`.

**Validation rules**

| Field | Rule |
|---|---|
| `name` | Optional in the DTO, but at least one editable field must be provided by the service |
| `name` | Must be a string |
| `name` | Must not be empty or whitespace-only |
| `name` | Must contain between 2 and 100 characters after trimming |
| Other fields | Rejected by the global validation pipe |

The current implementation supports updating `name` only. Fields such as `id`, `email`, `role`, and `passwordHash` cannot be changed through this endpoint.

**Possible errors**

- `400 Bad Request` â€” invalid name, empty update, or unexpected property.
- `401 Unauthorized` â€” token is missing or invalid.
- `404 Not Found` â€” the user record no longer exists.

## 4. Security considerations

- Both endpoints are protected by `JwtAuthGuard`.
- The authenticated user ID is taken from the validated request identity.
- Clients cannot select another user's profile by supplying a different user ID.
- The response uses an explicit Prisma selection of safe fields.
- `passwordHash` is excluded from profile responses.
- Global validation uses `whitelist`, `forbidNonWhitelisted`, and `transform`.

## 5. Testing

The profile API is covered by:

- Service unit tests for profile retrieval, safe field selection, name updates, empty updates, and missing-user handling.
- Controller unit tests for delegation to the service using the authenticated user ID.
- E2E tests for authentication, profile retrieval, profile updates, validation errors, unexpected properties, and safe responses.

The current E2E suite uses an in-memory Prisma mock. Database-backed integration testing against PostgreSQL is a separate verification step.

## 6. Current scope and future extensions

The current implementation supports reading the authenticated user's profile and changing their display name. Additional fields such as education, skills, career goals, and profile completeness can be introduced in future changes with appropriate schema, validation, authorization, and test updates.
